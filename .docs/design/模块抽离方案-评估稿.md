# NomiKit 模块抽离方案（评估稿）

> 状态：方案评估 · 2026-11-01
> 范围：把非核心模块外置为独立仓库、以依赖方式消费。本文只给结论与路线，不含实施改动。

## 1. 结论

- 方向成立，但 **现在拆不动**——缺的不是模块划分，是发布基建。
- **不按模块拆仓**（39 个模块 ≠ 39 个仓），按 **发布单元**拆成 5~6 个仓。
- 顺序固定：先发布基建 → 再低层无 UI 库 → 最后核心与 UI 强耦合层。

## 2. 现状（已核实）

| 项       | 现状                                                                         |
|----------|------------------------------------------------------------------------------|
| 模块     | 44 条 `include`，5 个聚合目录，39 个实模块                                   |
| 发布设施 | 无 `maven-publish`、无 `group`/`version`、无签名、无 CI                      |
| 约定插件 | `buildSrc` 4 个预编译脚本，仓库外不可 apply                                  |
| 依赖引用 | 近百处 `projects.*`（TYPESAFE_PROJECT_ACCESSORS）                            |
| 工具链   | Kotlin 2.3.0 / AGP 9.2.0 / CMP 1.12.2 / KSP 2.3.3，单一 `libs.versions.toml` |

## 3. 拆仓前必须解掉的 5 个阻塞

| # | 阻塞                                                   | 位置                                       | 后果                                       |
|---|--------------------------------------------------------|--------------------------------------------|--------------------------------------------|
| 1 | 约定插件是仓内预编译脚本                               | `buildSrc/`                                | 新仓无法 apply，只能复制 buildSrc          |
| 2 | `commonTest` 无条件注入 `:core:testing`                | `multiplatform-lib-targets.gradle.kts:216` | 模块一外置即编译失败                       |
| 3 | Android namespace 由 `Project.path` 推导               | `build.kt:166`                             | 搬迁即改 AAR namespace，消费方重新解析资源 |
| 4 | KoinBoot 按仓内依赖图生成代码，import 硬编码 `ciyin.*` | `koin-boot-initializer.gradle.kts:77`      | `component/*` 无法外置                     |
| 5 | target 矩阵由本机 `local.properties` 开关决定          | `properties.kt:142`                        | 发布库的 target 集必须固定，不能随机器变   |

附带需先修的分层违规（与 `AGENTS.md` 声明的 `app → business/feature/component → core` 冲突）：

- `core:application` → `component:koin`（core 反向依赖 component）
- `component:media-library` / `component:media-directory` → `feature:*`

## 4. 拆 / 不拆

| 模块                                                                            | 结论               | 理由                                                             |
|---------------------------------------------------------------------------------|--------------------|------------------------------------------------------------------|
| `core:lang` `io` `serialization` `testing`                                      | 首批拆             | 零 Compose、零业务、API 面窄                                     |
| `core:coroutines` `system`                                                      | 第二批拆           | 需先切断对 `core:platform` 的实现依赖                            |
| `core:platform`                                                                 | 最后拆，且先拆两半 | 因 `LocalContext` 而 `api` 了 Compose runtime/ui，是全仓编译基座 |
| `core:ui-preview` `ui-foundation` `material` `application`                      | 不拆               | 设计系统 + KoinBoot 装配属同一演进单元                           |
| `feature:file-downloader` `file-picker` `parser` `parser-site` `sdwebui` `ai-*` | 优先拆             | 协议封装型，独立价值最高                                         |
| `feature:video-player` `media-*` `permissions`                                  | 中期拆             | 平台绑定重但边界清晰                                             |
| `component/*`                                                                   | 不拆               | 依赖仓内 Gradle 依赖图生成代码                                   |
| `business/*` `app/*`                                                            | 不拆               | 应用特有                                                         |

## 5. 目标结构

```text
nomikit-build-logic   Gradle 插件 + 共享 version catalog   ciyin.build:*
nomikit-core          lang io serialization testing ...    ciyin.core:*
nomikit-ai            ai-core 引擎 sdwebui ai-integrate     ciyin.ai:*
nomikit-parser        parser parser-site                   ciyin.parser:*
nomikit-media         downloader picker media-* player ...  ciyin.media:*
NomiKit               应用 + 设计系统 + component 装配       —
```

关键： **发布单元 = 一个仓**，单元内仍是多模块库，不追求一模块一仓。

## 6. 分期路线

| 阶段 | 动作                                                | 验收                                             |
|------|-----------------------------------------------------|--------------------------------------------------|
| P0   | 单仓内打通可发布性，不动目录                        | `publishToMavenLocal` 后空白工程加一行坐标能编译 |
| P1   | `buildSrc` → 独立 `build-logic` 仓，插件以 id apply | 全仓编译/测试与迁移前一致                        |
| P2   | 拆 `nomikit-core`，用 composite build 过渡          | 源码不改，回归全绿                               |
| P3   | 切真实 Maven 坐标（先 GitHub Packages）             | 干净 clone、无本地缓存可构建                     |
| P4   | 逐域拆 ai / parser / media                          | 每域外部消费冒烟仓通过                           |

两段关键代码：

```kotlin
// P1：把仓内预编译脚本变成可发布插件
// build-logic/build.gradle.kts
gradlePlugin {
    plugins {
        create("kmpLibrary") {
            id = "ciyin.kmp.library"
            implementationClass = "ciyin.buildlogic.KmpLibraryPlugin"
        }
    }
}

// P2：过渡期源码不改，用依赖替换
// NomiKit/settings.gradle.kts
includeBuild("../nomikit-core") {
    dependencySubstitution {
        substitute(module("ciyin.core:io")).using(project(":io"))
    }
}
```

## 7. 每个外置模块的准入门槛

- `commonMain` 无 Compose 依赖（该模块本身就是 UI 库除外）。
- `commonTest` 只依赖已发布坐标，不依赖仓内非发布模块。
- `api` / `implementation` 边界正确——发布后 `implementation` 不再向消费方传递。
- 默认验证链只跑 `commonTest` / `desktopTest`；`desktopIntegrationTest` 保持手动。

## 8. 代价

1. **改一行要发版**——用 `includeBuild` + `publishToMavenLocal` 联调缓解。
2. **版本漂移**——靠共享 version catalog（`from("ciyin.build:versions:x")`）压住，这是多仓最大的日常成本。
3. **CI 从零建**——当前无任何 workflow；多仓没有 CI 无法维护，应在 P0 一并建立。

## 9. 建议

1. 先做 P0 + P1，不改业务代码，风险最低；做完再决定拆几个仓。
2. 设计系统与 `component/*` 永远留在应用仓。
3. `core:platform` 最后动，且先拆成 `platform` + `platform-compose` 两个 artifact。
4. 若目标只是“遏制骨架膨胀”而非对外发布，更便宜的中间态是：保持单仓，按发布单元分组，并给每个单元加“公共
   API 冻结”检查。
